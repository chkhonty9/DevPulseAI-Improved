# DevPulseAI Improvement Plan

## Guardrails

- Do not modify `../devpulse_ai`.
- Do not depend on `../devpulse_ai` at runtime.
- Keep source collection deterministic; it is a utility, not an AI agent.
- Use the protected GetQHSE gateway for default local reasoning; keep optional
  user-entered providers behind the same provider-neutral interface.
- Do not silently replace failed AI calls with heuristic results.
- Do not add a new orchestration framework unless the Python pipeline becomes
  insufficient.

## Stage 0 — Reproduce and verify the baseline

Create an independent copy of the useful original behavior:

- GitHub, arXiv, Hacker News, Medium, and Hugging Face adapters
- Signal normalization and deduplication
- Relevance Agent
- Risk Agent
- Synthesis Agent
- CLI runner
- Streamlit interface
- Baseline verification

At this stage behavior remains equivalent to the original. We record what
works and what fails before improving it.

Success criteria:

- The new project imports independently.
- Mock verification passes.
- The UI launches.
- The original project remains unchanged.

## Stage 1 — Provider foundation

- Add a provider-neutral structured LLM interface.
- Implement OpenAI-compatible clients behind one shared interface.
- Local development reads a protected GetQHSE gateway key.
- Deployment requests a masked user key.
- Return model, latency, and token usage from each request.

Success criteria:

- Provider, settings, agent-integration, and secret-redaction tests pass.
- The UI can make an explicit connection test after a valid key is supplied.

## Stage 2 — Honest AI failure handling

Status: **implemented and verified**

- Remove silent heuristic fallback from production reasoning paths.
- Retry one temporary or malformed response at most once.
- Show a clear error when the selected provider is unavailable or returns
  invalid output.
- Keep heuristic behavior only in explicitly named mock tests.

Success criteria:

- A failed AI call is never presented as successful AI analysis.

## Stage 3 — Strict Pydantic contracts

Status: **implemented and verified**

Introduce validated models for:

- `DeveloperProfile`
- `Signal`
- `RelevanceResult`
- `RiskResult`
- `EvidenceItem`
- `IntelligenceDigest`
- `CriticResult`
- `PipelineResult`

Success criteria:

- Missing, extra, or invalid agent fields fail validation visibly.

## Stage 4 — Context-aware relevance

Status: **implemented and verified**

- Add technologies, interests, and experience level to the UI.
- Include the developer profile in relevance analysis.
- Return matched technologies, matched interests, reasoning, and actionability.

Success criteria:

- The same signal receives meaningfully different scores for different
  developer profiles.

## Stage 5 — Evidence-constrained risk

Status: **implemented and verified**

- Validate risk levels.
- Require explicit concerns and recommended actions.
- Prevent invented CVEs, versions, and migration requirements.

Success criteria:

- Risk claims can be traced to the supplied signal text.

## Stage 6 — Real AI synthesis with citations

Status: **implemented and verified**

- Make synthesis actually call the model.
- Build an immutable evidence pack with stable IDs.
- Require every recommendation to cite evidence IDs.

Success criteria:

- The digest is generated by AI and all recommendations are traceable.

## Stage 7 — Independent critic

Status: **implemented and verified**

- Evaluate groundedness, profile relevance, and completeness.
- List unsupported claims.
- Combine AI evaluation with deterministic ID checks.

Success criteria:

- A report with an unknown signal or evidence ID fails review.

## Stage 8 — Bounded revision

Status: **implemented and verified**

- Send critic feedback back to synthesis.
- Allow no more than two revisions.
- Return `needs_review` when the final attempt still fails.

Success criteria:

- A controlled defective report either improves or is explicitly rejected.

## Stage 9 — Evaluation engineering

Status: **implemented and verified with an 18-case GetQHSE baseline**

- Add 15–20 manually reviewed cases.
- Measure relevance agreement, invalid output rate, groundedness, latency,
  tokens, cost, and revision success.

Success criteria:

- Improvements are supported by reproducible metrics rather than claims.

## Stage 10 — UI observability

- Show the developer profile and matched context.
- Show actual prioritized signals.
- Show evidence citations.
- Show critic scores and revision history.
- Show model and usage information.

Success criteria:

- A user can understand why every item was selected and whether the report
  passed evaluation.
